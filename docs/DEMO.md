# Демо и питч: 7 минут

Структура строго по ТЗ (§4): проблема → подход → архитектура пайплайна →
живое демо → архитектура аудита → выводы. Тайминг рассчитан на 7:00 с запасом
на вопросы внутри демо.

## Подготовка (до выхода на сцену)

```bash
cp .env.example .env
docker compose up --build          # ждём, пока ollama скачает модели
curl http://localhost:8000/api/health   # llm.available = true
```

Чек-лист:

- [ ] `data/templates/` — незнакомый шаблон, который команда не видела
      (не один из трёх VK: подойдёт любой PPTX из интернета).
- [ ] `data/templates/` — контент-пакет (PPTX/DOCX/TXT) с фактами для брифа.
- [ ] Браузер открыт на http://localhost:3000, окно на весь экран, зум 100%.
- [ ] Второй таб: http://localhost:8000/docs (на случай вопроса про API).
- [ ] Заготовлен бриф в буфер обмена (текст ниже).
- [ ] Проверены провайдеры: `python tools/llm_check.py --json-call` и `--vlm`
      (печатает провайдера, модель, доступность и наличие ключа без его значения).
- [ ] Заранее прогнан один прогон, чтобы кэш миниатюр был тёплым
      (второй прогон на демо идёт заметно быстрее).
- [ ] Репетиция уложилась в бюджет: `python tools/demo_rehearsal.py`
      (печатает время каждой стадии и сверяет с 7 минутами).
- [ ] Таймер на 7:00 на видном месте.

**План Б.** В панели отчёта есть селекторы провайдера и кнопка «применить»
(`POST /api/provider`): если внешний шлюз отвалился, переключите планировщик на
`offline` — сервис продолжит собирать колоду офлайн-планировщиком, аудит и
экспорт работают полностью. Переключение мгновенное, без перезапуска. Второй
вариант — отключить только VLM (`vlm: off`), если он тормозит.

Бриф для демо (пример, подставьте свой):

> Платформа внутренней аналитики: за квартал время подготовки отчётов
> сократилось на 40%, автоматизированы 12 рутинных задач, охват — 5
> подразделений. Платформой пользуются 2000 сотрудников еженедельно. План —
> подключить 10 отделов к концу года, внедрить ML-предсказания выручки.

## 1. Проблема (0:50)

«Каждую неделю в компании рождаются десятки презентаций. Автор пишет текст, а
дальше начинается ручная работа: подобрать макет, подвинуть блоки, найти иконку,
перекрасить диаграмму в корпоративный цвет. Модели уже хорошо пишут содержание —
и совершенно не умеют воспроизводить дизайн-систему: они не читают чужой
шаблон как набор правил.

Мы закрываем именно этот разрыв: сервис читает **произвольный** PPTX-шаблон,
извлекает из него дизайн-систему и собирает по ней новую презентацию — так, что
её не стыдно показать клиенту.»

## 2. Подход (0:50)

«Три решения, которые определяют всё остальное:

1. **Шаблон — это данные, а не код.** Мы разбираем файл: тему, макеты, палитру,
   шрифты, типографическую шкалу, поля, фирменные элементы. На выходе —
   JSON-профиль. Ни одного знания о бренде в коде нет: на финале будет
   незнакомый шаблон, и он обработается так же.
2. **Роли макетов выводятся из структуры, а не из имени.** Титул, раздел,
   оглавление, контент, финал — по типам и количеству плейсхолдеров, картинок,
   свободных текстовых фигур и геометрии заголовка. Имя макета — только
   подсказка. Поэтому шаблон с макетами `Slide 1…N` работает.
3. **Всё локально и на открытых весах.** Qwen2.5 через Ollama, VLM — Qwen2.5-VL,
   эмбеддинги — BGE-M3. Ни одного платного вызова.»

## 3. Архитектура пайплайна (0:50)

Показать схему из `docs/ARCHITECTURE.md` и пройти по слоям:

«Слои общаются только через контракты: парсинг → JSON-профиль, генерация →
Pydantic-схема колоды, вёрстка → план виджетов, рендер → нативные объекты PPTX,
аудит → список проблем с координатами, экспорт → PPTX/PDF/HTML. Вёрстка не
читает PPTX, рендер не ходит в модель, аудит не меняет колоду — поэтому каждую
часть можно тестировать отдельно. Сейчас в репозитории 103 теста и сквозной
скрипт `scripts/e2e.sh`.»

## 4. Живое демо (2:40)

Пошагово, без переключений окна:

1. **Загрузка незнакомого шаблона** (10 с). «Файл, которого сервис не видел.
   Обратите внимание: в интерфейсе нет ни одного упоминания VK.»
2. **Контент-пакет** (10 с). Загрузить PPTX/DOCX/TXT: «Пакет разобран на слайды,
   тезисы, таблицы, цифры и изображения. Числа отсюда — единственный источник
   фактов.»
3. **Бриф и запуск** (10 с). Нажать «Сгенерировать 3 варианта».
   Пока идёт генерация (обычно 20–60 с с моделью): «В это время сервис разбирает
   шаблон, планирует структуру, верстает три варианта и прогоняет два аудита.»
4. **Три варианта** (40 с). Переключить `compact` → `cards` → `split`:
   «Один контент, один шаблон, три оси различий: плотность, группировка,
   порядок и способ визуализации данных. Все три одинаково валидны — это
   проверено аудитом, а не на глаз.»
5. **Аудит** (40 с). Показать список проблем, красные рамки на миниатюре:
   «Слева детерминированные проверки: геометрия, токены шаблона, контраст,
   плотность. Ниже — контекстуальные: VLM по 11 вопросам ТЗ и проверка опоры на
   источник через эмбеддинги.»
6. **Авто-фиксы** (30 с). Отметить 2–3 проблемы, нажать «Исправить выбранное»:
   «Фиксы детерминированные, без модели: разбить слайд, сменить макет, уменьшить
   кегль на ступень шкалы, заменить таблицу диаграммой. В отчёте видно, что
   исправлено, а что пропущено и почему.»
7. **Экспорт** (20 с). Скачать PPTX, открыть в PowerPoint и кликнуть по блоку:
   «Все объекты нативные и редактируемые: текст, таблицы, диаграммы, картинки.
   Растровых слайдов нет. PDF собирается LibreOffice, HTML — отдельная
   презентация.»

Если что-то пойдёт не так: генерация уже была прогнана заранее — открыть готовое
задание (`data/jobs/`) и показать результат; при недоступности модели сервис
честно переключается на офлайн-планировщик, и это видно в отчёте.

## 5. Архитектура аудита (1:10)

«Аудит — часть пайплайна, а не внешняя проверка. Он разделён на три слоя:

| Слой | Что проверяет | Почему так |
|---|---|---|
| Детерминированный (24 кода) | геометрия, наложения, обрезка, шрифты, кегли по шкале, цвета, контраст WCAG, плотность, таблицы, диаграммы, заглушки, дубли, растровые слайды | один и тот же файл — один и тот же результат, значит, годится для CI и для авто-фиксов |
| Контекстуальный (VLM, 11 вопросов ТЗ) | заголовок-вывод, соответствие содержанию, факты, опечатки, язык колоды, логика соседей | смысл нельзя проверить координатами; в промпт передаются заголовки соседей и язык |
| Опора на источник (BGE-M3) | числа со слайдов против контент-пакета, семантическая близость, дубли по смыслу | ТЗ требует «все цифры и факты из исходников» — это проверяемо численно |

Каждая проблема — это код, серьёзность, слайд, текст и координаты для подсветки.
Поэтому пользователь видит не «что-то не так», а конкретную рамку на слайде и
кнопку «исправить».»

## 6. Выводы (0:40)

«Что сделано: сервис читает произвольный шаблон, генерирует колоду по брифу,
верстает три варианта нативными объектами, аудитирует их детерминированно и
контекстуально, исправляет выбранные проблемы и экспортирует в PPTX, PDF и HTML.
Всё воспроизводится одной командой `docker compose up`, моделей — только
открытые веса.

Метрики: 103 теста, сквозной прогон по 7 шаблонам × 3 варианта — ноль ошибок и
замечаний, три варианта собираются за 1.7–5.4 секунды на CPU без моделей (бюджет
ТЗ — 300 секунд на колоду).

Дальше: text-to-image для иллюстраций, параллельный VLM-аудит, дообучение
планировщика на корпоративных брифах.»

1. Прогнать сценарий целиком с таймером минимум дважды.
2. Проверить, что демо работает на незнакомом шаблоне (скачать случайный PPTX).
3. Записать видео-демо без склеек (требование ТЗ) и приложить ссылку в README.
4. Отрепетировать ответы: «как выбирается макет?» → `role`/`kind`/`score` в
   профиле и `docs/DECISIONS.md` ADR-010; «почему аудит детерминированный?» →
   `docs/AUDIT.md`; «что с неизвестным шаблоном?» → `tools/audit_matrix.py
   --layouts` и мутированный шаблон `unfamiliar_mutated`.
