# Архитектура

## 1. Задача и границы

Сервис читает **чужой PPTX-шаблон** как набор правил дизайн-системы и собирает по
нему новую презентацию из текстового брифа. Ключевое требование ТЗ: решение не
заточено под конкретные шаблоны — ни одного знания о бренде, именах макетов или
фирменных цветах в коде нет.

Пайплайн разбит на слои с односторонними зависимостями:

```
 PPTX-шаблон ──▶ 1. ПАРСИНГ       template/  → TemplateProfile (JSON)
 контент-пакет ─▶ 2. КОНТЕНТ       content/   → ContentCorpus (текст + картинки)
 бриф ─────────▶ 3. ГЕНЕРАЦИЯ     planner/   → Deck (Pydantic-схема)
                  4. ВЁРСТКА       layout/    → план виджетов (rect + block + style)
                  5. РЕНДЕР        render/    → PPTX нативными объектами
                  6. АУДИТ         audit/     → Issue[] (+ авто-фиксы)
                  7. ЭКСПОРТ       export/    → .pptx / .pdf / .html
```

Правило зависимостей: слой знает только о слоях **слева** и о JSON-контрактах.
`layout/` не читает PPTX-байты, `render/` не ходит в LLM, `audit/` не мутирует
колоду, `export/` не знает про шаблон больше, чем токены дизайна.

## 2. Слои

### 2.1 Парсинг — `backend/app/template/`

| Файл | Ответственность |
|---|---|
| `parser.py` | `TemplateParser`: тема (цвета/шрифты), мастера и макеты с геометрией плейсхолдеров, реальные слайды, палитра по частоте, типографическая шкала, сетка/поля, паттерны композиции, роль и тип макета |
| `profile.py` | датаклассы профиля: `TemplateProfile`, `LayoutProfile` (role, kind, role_reason, score), `PlaceholderInfo`, `ColorToken`, `FontToken` |

Выход — **JSON-профиль** (`template_profiles/*.json`), который дальше читают
планировщик (объём контента), вёрстка (токены и сетка) и аудит (разрешённые
значения). Профиль — единственный мост между «чужим файлом» и остальным сервисом.

Роль макета выводится из **структуры** (типы и количество плейсхолдеров, картинки,
содержательные свободные текстовые фигуры, геометрия заголовка), имя макета —
только tie-breaker по однозначным словам. Каждое решение объяснимо: в профиле
хранится `role_reason`. Подробности — ADR-010.

### 2.2 Контент-пакет — `backend/app/content/`

| Файл | Ответственность |
|---|---|
| `importer.py` | `import_content_pack`: PPTX (слайд → заголовок, тезисы, таблицы, диаграммы, цифры, изображения), DOCX (`word/document.xml` + `word/media`), TXT/MD (разделы по заголовкам) → `ContentCorpus` |
| `corpus.py` | `ContentCorpus`/`CorpusSlide`/`CorpusTable`: текст для промпта (`text()`), список изображений (`image_prompt_block()`), поиск цифр с единицами, сохранение и загрузка в `data/corpora/{id}/` |

Корпус — единственный источник фактов для планировщика и база для grounding-проверки
«факт есть в исходниках» (этап 5). Изображения корпуса передаются в рендер реестром
`{ключ: байты}`, поэтому блоки `kind=image` встраиваются нативно.

### 2.3 Генерация — `backend/app/planner/`

| Файл | Ответственность |
|---|---|
| `planner.py` | оркестрация: промпты из `prompts/planner/`, вызов LLM, валидация ответа по Pydantic-схеме, ретраи с обратной связью об ошибках валидации |
| `llm.py` | `OllamaClient`: `/api/generate`, `/api/embed`, health-check, извлечение JSON из ответа |
| `fallback.py` | офлайн-планировщик: собирает валидную колоду из брифа и корпуса без модели (dev, CI, отказ LLM) |

Контракт — `Deck` в `backend/app/models/deck.py`: строгая Pydantic-схема
(перечисления типов слайдов, блоков, диаграмм, лимиты полей). Она одновременно
является описанием для LLM, валидатором ответа и внутренним представлением.

### 2.4 Вёрстка — `backend/app/layout/`

| Файл | Ответственность |
|---|---|
| `engine.py` | `DesignContext` (токены, `from_profile`) + `LayoutEngine.compose(slide, canvas)` → список виджетов `{widget, rect, block, style}`; три варианта: `compact`, `cards`, `split` |
| `geometry.py` | `Rect`, оценка числа строк и высоты текста, подбор кегля из шкалы, сетки, распределение высот |

Оси различий вариантов (обоснование — ADR-003):

| Вариант | Ось | Что делает |
|---|---|---|
| `compact` | плотность | полосы во всю ширину, минимальные отступы, порядок блоков сохраняется |
| `cards` | группировка | контент раскладывается в карточки-сетку 2×N |
| `split` | порядок + визуализация | данные (таблицы/диаграммы/фактоиды) поднимаются в отдельную колонку и рендерятся иначе |

### 2.5 Рендер — `backend/app/render/`

| Файл | Ответственность |
|---|---|
| `pptx_renderer.py` | `render_deck(deck, dc)` = `build_plan` + `render`: слайды создаются **на макетах шаблона**, заголовок кладётся в title-плейсхолдер, виджеты рисуются нативными объектами (текстбоксы, автофигуры, таблицы, диаграммы, картинки); исходные слайды шаблона удаляются вместе с частями пакета |
| `images.py` | пиксельные утилиты: конвертация цветов, кроп с сохранением пропорций, доминирующий цвет, наложение красных рамок проблем |
| `pdf.py` | `pptx_to_pdf` (LibreOffice headless), `pptx_to_pngs` (PDF → PNG через PyMuPDF) |

Жёсткие правила рендера:
1. слайд целиком растровой картинкой — запрещён (проверяется аудитом);
2. шрифты, цвета и кегли берутся только из профиля шаблона;
3. `add_picture` вписывает изображение с сохранением пропорций (contain), при
   отсутствии байтов остаётся нативный слот `image_slot`, а аудит отмечает
   `image_missing`;
4. область контента не заходит на заголовок макета (ADR-014).

### 2.6 Аудит — `backend/app/audit/`

| Файл | Ответственность |
|---|---|
| `checks.py` | детерминированные проверки по файлу: геометрия, наложения, обрезка, токены, контраст WCAG, плотность, таблицы/диаграммы, заглушки, дубли, растровый слайд |
| `vlm.py` | недетерминированные проверки: рендер слайда в PNG → Qwen2.5-VL по 11 вопросам ТЗ |

Результат — список `Issue {id, code, severity, slide, message, bbox, deterministic}`,
где `bbox` нормализован (0..1) и используется UI для красных рамок. Аудит **читает**
артефакт и колоду, но не изменяет их; авто-фиксы — отдельный слой (ADR-007).

### 2.7 Экспорт — `backend/app/export/`

`html.py` собирает автономную HTML-презентацию (слайд = секция, стрелки,
клавиатура) из той же `Deck` и токенов профиля — единый контент-контракт с PPTX.
PDF получается из PPTX через LibreOffice, поэтому визуально совпадает.

## 3. Оркестрация и API

`backend/app/pipeline.py` — тонкая склейка слоёв без бизнес-логики:

```
build_profile → plan_deck → render_variants(×3) → audit_variant(×3) → audit_vlm → html_export
```

Каждая стадия измеряется, время попадает в результат задания (`stages`), что
позволяет следить за бюджетом 5 минут (ADR-012).

`backend/app/api/main.py` — FastAPI: приём шаблона, брифа и контент-пакета,
фоновый воркер задания, отдача артефактов, миниатюры, аудит, авто-фиксы.
Задание асинхронное, UI опрашивает статус.

| Группа | Эндпоинты |
|---|---|
| Генерация | `POST /api/generate`, `GET /api/jobs/{id}`, `GET /api/jobs/{id}/info` |
| Артефакты | `GET /api/jobs/{id}/pptx`, `/pdf`, `/html`, `/thumb`, `/audit` |
| Контент | `POST /api/content/import`, `GET /api/content`, `/api/content/{id}`, `/api/content/{id}/image/{key}` |
| Служебные | `GET /api/health` |

## 4. Данные и хранилище

```
data/
  templates/    загруженные шаблоны и контент-пакеты (вне git)
  corpora/{id}/ разобранные контент-пакеты: corpus.json + images/
  jobs/         состояние заданий (переживает рестарт)
  cache/thumbs/ кэш миниатюр по хэшу PPTX
  e2e_out/      артефакты сквозных прогонов
```

## 5. Точки расширения

| Что | Где добавлять |
|---|---|
| новая проверка аудита | `audit/checks.py` — метод `_check_*`, регистрация в `audit()` |
| новое правило авто-фикса | `audit/fixes.py` — обработчик по `Issue.code` |
| новый тип блока | `models/deck.py` (`Block.kind`) → `layout/engine.py` (раскладка) → `render/pptx_renderer.py` (`_draw_item`) → `export/html.py` |
| новый вариант вёрстки | словарь `VARIANTS` + функция-компоновщик в `layout/engine.py` |
| новый формат контент-пакета | `content/importer.py` — функция `_import_*` и ветка в `import_content_pack` |
| новая модель/промпт | `prompts/<agent>/` + запись в `prompts/registry.json` |
| новый формат экспорта | `export/<format>.py`, подключение в API |
