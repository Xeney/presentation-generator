# Журнал архитектурных решений (ADR)

Формат: контекст → решение → следствия. Статусы: `принято`, `предложено`
(решение будет принято на указанном этапе), `отложено`, `заменено`.

---

## ADR-001. Локальный инференс через Ollama, только open weights

**Дата:** 2026-09-23 · **Статус:** принято

**Контекст.** ТЗ разрешает API-провайдеров только для моделей с открытыми весами
до 35B и требует самостоятельный инференс; бюджет команды 1–2 тыс. руб. на аренду
GPU для финального демо.

**Решение.** Единственный runtime — Ollama в Docker Compose: LLM, VLM и эмбеддинги
на одном порту, без ключей и платных вызовов. Модели: Qwen2.5-7B/14B-Instruct,
Qwen2.5-VL-7B, BGE-M3 (Apache 2.0 / MIT).

**Следствия.** (+) нулевая стоимость, воспроизводимость, отсутствие утечки данных
за периметр. (+) один и тот же код работает и на CPU, и на GPU. (−) требования к
RAM/VRAM у пользователя; (−) на CPU генерация медленнее бюджета 5 минут — для
демо нужен GPU. Митигация: флаг `DISABLE_LLM` и офлайн-планировщик (ADR-005).

## ADR-002. Бинарные шаблоны и контент-пакеты не хранятся в git

**Дата:** 2026-09-23 · **Статус:** принято

**Контекст.** Комплект: 3 шаблона VK + контент-пакет, суммарно ≈ 90 МБ PPTX;
артефакты прогонов (`data/`) — ещё ≈ 260 МБ. Git LFS усложняет клонирование
экспертами и имеет лимиты трафика.

**Решение.** `*.pptx`, `*.pdf`, `*.docx`, `data/`, `exports/` исключены через
`.gitignore`. В репозитории остаются JSON-профили (`template_profiles/`) и
маленькие синтетические фикстуры для тестов. Инструкция по получению шаблонов —
`docs/README.md` §3.

**Следствия.** (+) репозиторий лёгкий и клонируется мгновенно. (+) сервис
принципиально не зависит от конкретных файлов: любой PPTX грузится через UI.
(−) для проверки на шаблонах VK эксперту нужно взять их из датасета организаторов.
(−) модульные тесты, требующие VK-шаблоны, скипаются при их отсутствии — вместо
них используются генерируемые фикстуры (`tests/fixtures/make_fixtures.py`).

## ADR-003. Три варианта вёрстки: плотность, группировка, порядок+визуализация

**Дата:** 2026-09-23 · **Статус:** принято

**Контекст.** ТЗ требует три визуально различимых, но одинаково валидных варианта
на одном шаблоне и контенте; ось различий команда определяет и обосновывает сама.

**Решение.** Оси выбраны так, чтобы варианты различались на уровне композиции, а
не косметики:

| Вариант | Ось | Композиция |
|---|---|---|
| `compact` | плотность | полосы во всю ширину, минимальные зазоры, порядок блоков из колоды сохраняется |
| `cards` | группировка | блоки раскладываются в карточки-сетку 2×N, каждый блок в своей рамке |
| `split` | порядок + визуализация | блоки данных (таблица/диаграмма/фактоиды) отделяются в колонку, поднимаются выше текста, меняется способ подачи |

**Следствия.** (+) различия видны на уровне структуры слайда и объяснимы
одним предложением каждый; (+) все три используют только токены шаблона и
проходят один и тот же аудит. (−) `split` может выглядеть пустым при одном
блоке — компоновщик откатывается к `compact`-раскладке.

## ADR-004. Pydantic-схема `Deck` — единый контракт пайплайна

**Дата:** 2026-09-23 · **Статус:** принято

**Контекст.** Ответ LLM нужно одновременно описывать модели, валидировать и
использовать как внутреннее представление; ТЗ требует строгую схему.

**Решение.** `backend/app/models/deck.py` — единственный источник правды.
Схема подставляется в промпт (`Deck.model_json_schema()`), ответ валидируется
ею же, ошибки валидации возвращаются модели на исправление (ретраи).

**Следствия.** (+) невозможность «грязных» данных в вёрстке; (+) лимиты
гайдлайнов (≤6 буллетов, ≤5 серий, ≤7×5 таблица) зафиксированы декларативно.
(−) жёсткость схемы требует ретраев; (−) расширение типов блоков затрагивает
три слоя (схема → вёрстка → рендер).

## ADR-005. Офлайн-планировщик как обязательный fallback

**Дата:** 2026-09-23 · **Статус:** принято

**Контекст.** Демонстрация и тесты не должны зависеть от наличия Ollama; ТЗ
требует устойчивости решения.

**Решение.** `planner/fallback.py` собирает валидную колоду детерминированно из
брифа и контент-пакета, без выдуманных фактов. Включается при `DISABLE_LLM=true`,
недоступности Ollama или исчерпании ретраев валидации. Факт использования LLM
пишется в результат задания (`planner.used_llm`).

**Следствия.** (+) CI и UI-разработка не требуют моделей; (+) сервис деградирует
корректно. (−) fallback-контент беднее: тезисы — предложения из брифа без
переупаковки. В отчёте честно отображается «offline-fallback».

## ADR-006. PDF и миниатюры — LibreOffice headless, а не свой рендерер

**Дата:** 2026-09-23 · **Статус:** принято

**Контекст.** Нужны `.pdf` и PNG-миниатюры слайдов для UI и VLM-аудита.
Собственный рендерер PPTX не даст точного соответствия PowerPoint.

**Решение.** `soffice --headless --convert-to pdf` в контейнере backend;
PDF → PNG через PyMuPDF. Ошибка конвертации возвращается как HTTP 503 с
пояснением, а не 500.

**Следствия.** (+) PDF совпадает с PPTX «глазами» офисного пакета, миниатюры
честные. (−) образ backend тяжелее (1.23 ГБ с LibreOffice); (−) экспорт
недоступен при локальном запуске без `soffice`; (−) время конвертации
учитывается в бюджете 5 минут.

**Проверено в контейнере (2026-09-25).** Два дефекта образа, найденные при
прогоне e2e внутри Docker: (1) не был установлен `libreoffice-impress` — Writer
не открывает PPTX («source file could not be loaded»), поэтому PDF-экспорт и
миниатюры в контейнере не работали вовсе, а VLM-аудит не получал картинок;
(2) не было фирменного `Play` и метрического аналога Calibri — LibreOffice
подставлял DejaVu, то есть PDF и миниатюры показывали не ту типографику, что
лежит в PPTX. Добавлены `libreoffice-impress`, `fonts-crosextra-carlito`
(метрически совместим с Calibri), `fonts-crosextra-caladea`, `fonts-noto-core`
и загрузка `Play` из `google/fonts` (SIL OFL) с мягким падением без сети.
Проверка: `fc-match Calibri → Carlito`, `fc-match Play → Play`, миниатюры
14 слайдов по 338 КБ, PDF открывается.

## ADR-007. Аудит не мутирует колоду, авто-фиксы — отдельный слой

**Дата:** 2026-09-23 · **Статус:** принято

**Контекст.** ТЗ требует: система визуализирует проблемы, пользователь выбирает,
что исправить. Смешение «найти» и «исправить» затрудняет тестирование и делает
аудит непредсказуемым.

**Решение.** `audit/checks.py` только читает артефакт и возвращает `Issue[]`.
Исправления — отдельный слой `audit/fixes.py`, применяемый по выбранным
`issue.id` через `POST /api/jobs/{id}/fix`. Каждый фикс детерминирован и
описывает, что именно изменил. Библиотека фиксов: разбить слайд, объединить
слайды, заменить визуал (таблица ↔ диаграмма, убрать битую иллюстрацию), сменить
макет (`Slide.layout_hint`), уменьшить кегль на ступень шкалы
(`Slide.type_scale_step`), удалить блок-заглушку, удалить дубль.

**Следствия.** (+) аудит можно запускать многократно без побочных эффектов;
(+) фиксы тестируются по отдельности; (+) пользователь контролирует изменения;
(+) проблемы, которые нельзя решить правкой контента (`raster_slide`, чужие
гарнитуры, низкий контраст шаблона), не имитируются, а пропускаются с причиной.
(−) после фиксов нужен повторный рендер: байты шаблона хранятся в задании
(в памяти), поэтому задание живёт до перезапуска сервиса — постоянное хранилище
заданий появится в этапе 6.

## ADR-008. Производные цвета: смеси разрешены для заливок, но не для текста

**Дата:** 2026-09-23 · **Статус:** принято (этап 3)

**Контекст.** Вёрстка делает светлые подложки карточек смешением акцента с фоном
(`mix(accent, bg, 0.86)`). Такие оттенки не входят в палитру шаблона, и проверка
цвета ругала собственный рендер.

**Варианты.** (а) отказаться от смешения; (б) разрешить производные только для
заливок; (в) дописывать производные токены в профиль при парсинге.

**Решение.** Вариант (б). Формальное правило в аудите: заливка допустима, если
это точный цвет палитры **или** точка на отрезке между двумя цветами палитры в
RGB (допуск 14/255, `Audit.is_derived_color`). Для текстовых runs правило строгое:
только точные токены палитры, темы или список текстовых цветов профиля.

**Следствия.** (+) брендовая палитра остаётся замкнутой относительно
осветления/затемнения — это стандартная практика дизайн-систем; (+) аудит
по-прежнему ловит «левый» цвет, принесённый из другого шаблона или вставленный
руками; (+) текст защищён строже заливок (читаемость важнее декора).
(−) проверка заливок не смотрит в ячейки таблиц (у них нет `shape.fill`) —
зафиксировано как известное ограничение.

## ADR-009. VLM-аудит по одному варианту, остальные — по флагу

**Дата:** 2026-09-23 · **Статус:** принято

**Контекст.** VLM — самая дорогая стадия: конвертация в PDF, растеризация и
15 запросов к 7B-VLM. Утроение на три варианта не укладывается в бюджет 5 минут.

**Решение.** По умолчанию VLM-аудит выполняется для одного варианта (первого,
`compact`). Переменная `VLM_AUDIT_ALL_VARIANTS=true` включает проверку всех трёх,
`VLM_AUDIT_ENABLED=false` отключает стадию полностью. Детерминированный аудит
всегда выполняется для всех вариантов. Время стадии измеряется (`stages.vlm_s`,
`vlm.elapsed_s`, `vlm.per_slide_s`). После авто-фиксов VLM не пересчитывается:
результат помечается «не пересчитывался», чтобы устаревшая оценка не выглядела
свежей (пересчёт стоит около минуты и не входит в бюджет 5 минут).

**Следствия.** (+) бюджет времени контролируем; (+) пользователь видит разницу
между «файл соответствует правилам» (детерминированно, все варианты) и
«смысл в порядке» (VLM, один вариант). (−) при сравнении вариантов VLM-оценка
есть только у одного — это указано в UI.

## ADR-010. Роль и тип макета выводятся из структуры, имя — только tie-breaker

**Дата:** 2026-09-23 · **Статус:** принято (этап 2)

**Контекст.** Ключевой риск защиты: на финале шаблон неизвестный. Изначально роль
угадывалась по ключевым словам в имени макета, что не работает для имён вида
`Slide 1` или на другом языке, и давало перекос (VK_WorkSpace: 11 из 15 макетов
помечены `title` без обоснования).

**Решение.** Порядок принятия решения в `TemplateParser._classify_layout`:

1. **Данные однозначны**: таблица или диаграмма на макете → `content` + тип
   `table`/`chart`.
2. **Семантическая роль по имени** — но только по однозначным словам:
   `спасибо/финал/контакты/qr` → `final`, `содержание/оглавление/agenda` →
   `agenda`, `раздел/разделитель/section` → `section`, `титул/обложка/cover/
   title slide/title only` → `title`, `контент/заголовок/текст/пункт` →
   `content`. Общие слова вроде просто `title` намеренно не используются, иначе
   «Title and Content» стал бы обложкой.
3. **Структура**, если имя неинформативно: считаются плейсхолдеры
   (title/body/subtitle/picture/table), картинки и **содержательные свободные
   текстовые фигуры** (многие шаблоны держат контентную область именно так),
   а также геометрия заголовка. Правила: нет заголовка → `blank`/`multi_column`;
   заголовок + подзаголовок → `title`; заголовок без контента по центру слайда →
   `title`, у верха → `section`; картинка + текст → `image_text`; 4+ блока →
   `multi_column`; иначе `bullets`.

Дополнительно в профиль пишутся `kind` (композиционный тип: `bullets`,
`multi_column`, `image`, `image_text`, `table`, `chart`, `blank`) и
`role_reason` — текстовое обоснование. Рендер использует `kind` как бонус при
выборе макета под содержимое слайда.

**Замер после внедрения** (`python tools/audit_matrix.py --layouts`):

| Шаблон | Макетов | title | section | agenda | content | final |
|---|---|---|---|---|---|---|
| VK Tech (контент-пакет) | 39 | 6 | 2 | 6 | 20 | 5 |
| VK WorkSpace | 15 | 11 | – | – | 4 | – |
| ЛЦТ2026 | 23 | 1 | – | 1 | 21 | – |
| VK Education | 30 | 4 | 6 | – | 16 | 4 |
| synthetic 16:9 (фикстура) | 11 | 2 | 1 | – | 8 | – |
| unfamiliar (`Slide N`) | 11 | 1 | – | – | 10 | – |

Типы на ЛЦТ2026: `image_text` 6, `multi_column` 9, `bullets` 6, `image` 1,
`blank` 1 — то есть шаблон действительно разложен по композициям, а не по имени.

**Следствия.** (+) работает на шаблоне без говорящих имён (мутация `Slide N`
даёт корректный титульный макет по подзаголовку и центровке заголовка);
(+) каждое решение объяснимо в профиле; (+) отсутствие макетов нужной роли не
ломает пайплайн — рендер деградирует к контентным макетам. (−) для шаблонов,
где контент рисуется только на слайдах, макеты честно определяются как
`title/blank` (VK WorkSpace: 11) — это свойство шаблона, а не ошибка, и вёрстка
подставляет контентную сетку профиля.

## ADR-011. Text-to-image: отложено до подтверждения ресурсов

**Дата:** 2026-09-23 · **Статус:** отложено

**Контекст.** Генерация изображений — задача со звёздочкой для топ-10 (модель до
20B, Apache 2.0 / MIT). Слот `Block.kind = "image"` в схеме и рендере есть.

**Решение.** Сначала закрываются обязательные пункты ТЗ (парсинг, генерация,
вёрстка, аудит, три варианта, экспорт). Картинки в слайдах на этом этапе берутся
из контент-пакета (изображения PPTX) и встраиваются нативно. Локальная
text-to-image (FLUX.1-schnell / Sana) подключается, если после этапа 7 остаётся
время и есть GPU ≥ 12 ГБ VRAM.

**Следствия.** (+) обязательная часть не страдает; (−) при отказе в
`docs/MODELS.md` §4 фиксируется обоснование — так требует ТЗ.

## ADR-012. Бюджет времени и замеры стадий

**Дата:** 2026-09-23 · **Статус:** предложено (замеры — этап 7)

**Контекст.** ТЗ: колода 10–15 слайдов генерируется не более 5 минут.

**Решение.** Каждая стадия измеряется и пишется в результат задания
(`stages`: `parse_s`, `plan_s`, `render_s`, `audit_s`, `grounding_s`, `vlm_s`,
`fix_s`, `total_s`), а в UI отображается в отчёте. При превышении бюджета VLM
переводится в режим «только один вариант» или отключается флагом.

**Замеры без моделей** (`scripts/e2e.sh`, 7 шаблонов × 3 варианта, CPU):

| Стадия | Время |
|---|---|
| парсинг шаблона | 0.4–1.7 с (39 макетов VK Tech — 1.7 с) |
| планирование (офлайн-fallback) | < 0.05 с |
| рендер одного варианта | 0.5–1.0 с |
| детерминированный аудит одного варианта | 0.26–0.36 с |
| **три варианта целиком** | **1.7–5.4 с** |
| весь прогон по 7 шаблонам | 6 с |

**Замеры на живом AITUNNEL** (`qwen3.5-9b`, репетиция демо
`tools/demo_rehearsal.py`, шаблон ЛЦТ2026 + контент-пакет VK Tech):

| Стадия | Время |
|---|---|
| здоровье провайдера | 0.8 с |
| разбор контент-пакета (54 слайда, 60 картинок) | 1.1 с |
| планирование колоды (10 слайдов) | 10.6 с (с первой попытки) |
| рендер трёх вариантов | 1.9 с |
| детерминированный аудит ×3 | 0.9 с |
| grounding (эмбеддинги `qwen3-embedding-8b`) | 2.3 с |
| VLM-аудит одного варианта (10 слайдов) | 89.9 с (≈ 9 с на слайд) |
| авто-фиксы | 2.8 с |
| экспорт PPTX ×3 + PDF + HTML | 25.3 с |
| **итого демо-прогон** | **216.4 с из 420 с** |

Девять вариантов (3 шаблона × 3 вёрстки) — 379.9 с суммарно, по 120–135 с на
шаблон, то есть каждый в бюджете 300 с.

**Замеры внутри Docker** (`docker compose build` + e2e в контейнере, те же
шаблоны и контент-пакет):

| Стадия | Хост | Docker |
|---|---|---|
| планирование | 10.6–68.6 с | 10.7 с |
| рендер ×3 | 1.9 с | 2.6 с |
| детерминированный аудит ×3 | 0.9 с | 1.3 с |
| grounding | 2.3 с | 4.9 с |
| VLM ×1 | 89.9 с | **23.1 с** |
| **итого на шаблон (3 варианта)** | 120–135 с | **42–57 с** |

VLM в контейнере вдвое быстрее, чем на хосте: картинки уменьшаются до 1280 px,
запросы идут параллельно (3 воркера), а стадия ограничена общим бюджетом 180 с
с честной пометкой непроверенных слайдов.

Наблюдения: планирование 10–22 с (было 55–345 с до отключения «размышлений»);
VLM — самая дорогая стадия и самая переменчивая (2.7–9 с на слайд в зависимости
от загрузки шлюза), поэтому она остаётся за флагом `VLM_AUDIT_ENABLED`, а
`VLM_AUDIT_ALL_VARIANTS` по умолчанию выключен.

**Следствия.** (+) узкие места видны в UI и логах; (+) демо предсказуемо и имеет
двукратный запас по бюджету; (+) на CPU без моделей сервис всё равно собирает
валидную колоду за секунды; (−) VLM-стадия зависит от внешнего шлюза — при
деградации отключается флагом или кнопкой «off» в UI (ADR-023).

## ADR-013. Версионирование промптов, конфигов и скиллов

**Дата:** 2026-09-23 · **Статус:** принято (манифест — этап 5)

**Контекст.** ТЗ: промпты и конфиги агентов лежат отдельными файлами и
версионируются; в результат нужно писать использованную версию.

**Решение.** Промпты и конфиги — только в `prompts/` (не в коде). Манифест

(`result["prompts"]`), UI их показывает. Хэши пересчитывает
`scripts/sync_prompts.py`, а тест `test_registry_is_in_sync_with_files` не даёт
закоммитить промпт, не попавший в манифест.

**Следствия.** (+) воспроизводимость результата: по хэшу видно, чем именно
сгенерирована колода; (+) изменение промпта не ломает историю. (−) хэши нужно
пересчитывать при правках — делается скриптом `scripts/sync_prompts.py`.

## ADR-014. Заголовок неприкосновенен: область контента обходит плейсхолдер

**Дата:** 2026-09-23 · **Статус:** принято

**Контекст.** Тело макета (body-плейсхолдер) на витринных слайдах нередко
покрывает весь слайд, включая заголовок. При первом же прогоне матрицы аудита
это дало наложения на титуле (Title Slide) и на разделе (Section Header:
заголовок стоит внизу, тело — сверху).

**Решение.** `Renderer._canvas` вызывает `_avoid_title`: если область контента
пересекается с прямоугольником заголовка макета, контент сдвигается **под**
заголовок; если места под ним меньше 0.6″, контент ставится **над** заголовком.
Если ни то, ни другое не проходит — область остаётся как есть (заголовок
перекрывается, но аудит об этом честно предупредит).

**Следствия.** (+) все три варианта вёрстки проходят аудит без замечаний на
титуле и разделе любого из проверенных шаблонов; (+) правило не привязано к
конкретным макетам — работает от геометрии профиля. (−) на нестандартных
макетах с «плавающим» заголовком возможен сдвиг контента в непривычное место.

## ADR-015. Дублирующие плейсхолдеры и осиротевшие части пакета

**Дата:** 2026-09-23 · **Статус:** принято

**Контекст.** Два дефекта, найденные при прогоне матрицы аудита:
1. `python-pptx` при `add_slide` уже клонирует плейсхолдеры макета, а рендер
   клонировал заголовок повторно — на каждом слайде оставался дубль заголовка;
2. удаление слайдов шаблона через `sldIdLst.remove()` не удаляло их части из
   пакета: файл раздувался, а новые слайды конфликтовали по именам частей
   (`Duplicate name: ppt/slides/slide1.xml`).

**Решение.** Дублирующий клон убран; пустые плейсхолдеры макета удаляются
(`_drop_empty_placeholders`), кроме заголовка; исходные слайды удаляются вместе
со связями (`prs.part.drop_rel`), и только после этого добавляются новые.

**Следствия.** (+) чистая структура файла, корректные имена частей, меньший
размер PPTX; (+) нет ложных наложений и пустых рамок в режиме правки.
(−) если макет использует непустые декоративные плейсхолдеры, они не попадут
на слайд — впрочем, декор должен жить на макете, а не на слайде.

## ADR-016. Задания и кэш миниатюр переживают рестарт

**Дата:** 2026-09-23 · **Статус:** принято (этап 6, реализовано)

**Контекст.** Сейчас состояние заданий хранится в памяти процесса, а миниатюры
пересобираются через LibreOffice на каждый HTTP-запрос. При рестарте контейнера
результаты теряются, а UI тормозит.

**Решение.** `JobStore`: метаданные в `data/jobs/{id}/job.json` (атомарная запись
через временный файл), артефакты — `template.pptx` и `{variant}.pptx` рядом; в
памяти LRU-кэш горячих заданий. `ThumbCache`: `data/cache/thumbs/{sha256(pptx)}/`
с файлами `{page}_{boxes}.png`; при первом запросе миниатюр один прогон
LibreOffice заполняет кэш всей колоды. TTL — `JOB_CLEANUP_HOURS`, очистка ленивая
и при старте сервиса.

**Следствия.** (+) UI отдаёт миниатюры мгновенно; (+) результаты не теряются при
перезапуске, авто-фиксы работают и после рестарта (шаблон читается с диска);
(+) кэш инвалидируется автоматически при изменении PPTX. (−) `data/` растёт
(до ~20 МБ на задание из-за шаблона) — очистка по TTL это ограничивает.

## ADR-017. Только токены шаблона: кегли из шкалы, диаграммы с подписями

**Дата:** 2026-09-23 · **Статус:** принято (этап 3)

**Контекст.** После включения проверок `font_size_not_in_scale` и
`chart_unlabeled` оказалось, что рендер сам их нарушает: производные размеры
(подпись в 0.35 от крупного числа, автор цитаты 14 pt, кегль ячейки 13 pt) не
входят в шкалу шаблона, а диаграммы рисовались без подписей данных и единиц.

**Решение.**
1. `Renderer._set_run_font` — единственная точка установки шрифта run; кегль
   проходит через `_snap_size`, который приводит значение к ближайшему из
   типографической шкалы шаблона. Жёстко заданные размеры (11/12/13/14 pt)
   больше не попадают в файл.
2. Таблица: кегль ячеек — минимальный подходящий размер шкалы, а не «13 по
   умолчанию».
3. Диаграмма: включаются подписи данных (`0"%"` при единице «%»), для круговых —
   проценты и имена категорий, при наличии `unit` — заголовок оси значений
   («Значение, %»), шрифт подписей/легенды/осей — из шкалы.

**Следствия.** (+) сгенерированный файл проходит собственный аудит на всех
шаблонах (0 ошибок, 0 замечаний); (+) диаграммы читаемы без пояснений спикера;
(−) на шаблонах с бедной шкалой (2–3 размера) подписи могут оказаться крупнее
привычных — это следствие требования «только токены шаблона».

## ADR-018. Tailwind + shadcn-подход вместо установки shadcn/ui через CLI

тянет конфигурацию и компоненты из сети и требует интерактивных ответов, что

проходят без обращений к реестру компонентов; (+) компоненты можно свободно
править под задачу; (+) ревьюеру видно весь код интерфейса. (−) обновление
примитивов делается вручную.

## ADR-019. Внешний OpenAI-совместимый шлюз — только для разработки

**Дата:** 2026-09-23 · **Статус:** принято

**Контекст.** ТЗ разрешает API лишь для моделей с открытыми весами до 35B и
запрещает платные вызовы, но разработка и отладка пайплайна без GPU удобнее с
внешней моделью. Нужен способ подключить любой OpenAI-совместимый шлюз, не
нарушая требований сдачи и не рискуя утечкой ключа.

**Решение.**
1. Добавлен второй клиент `OpenAICompatClient` с тем же интерфейсом, что у
   `OllamaClient` (health, list_models, generate_text/json, embed), и фабрика
   `get_llm_client()`; провайдер выбирается переменной `LLM_PROVIDER`
   (`ollama` по умолчанию).
2. Ключ читается только из `.env`/окружения, не логируется, вырезается из
   текстов ответов провайдера и никогда не попадает в сообщения об ошибках.
   `.gitignore` игнорирует любые `.env*`, кроме `.env.example`; тест
   `test_env_files_are_ignored_by_git` и `test_example_env_has_no_secret_values`
   стерегут это в CI.
3. Отказ шлюза (403/402/сеть) не роняет задание: планировщик переходит в
   офлайн-режим, VLM-аудит помечается недоступным, grounding проверяет числа.
4. В Docker Compose секреты передаются через `env_file` (в самом файле ключей
   нет).

**Следствия.** (+) пайплайн отлаживается без GPU, интерфейсы клиентов
взаимозаменяемы; (+) сдача остаётся соответствующей ТЗ при `LLM_PROVIDER=ollama`;
(+) утечка ключа в репозиторий закрыта технически. (−) `docker compose config`
печатает разрешённые значения, включая ключ — не публикуйте его вывод;
(−) VLM-аудит и семантический grounding зависят от наличия vision- и
embedding-моделей у шлюза.

## ADR-020. AITUNNEL как провайдер на отборочном этапе

**Дата:** 2026-09-23 · **Статус:** принято

**Контекст.** Для отборочного этапа нужен инференс, не требующий собственного
GPU: ТЗ разрешает внешний API только для моделей с открытыми весами до 35B.
AITUNNEL (`https://api.aitunnel.ru/v1`) — OpenAI-совместимый шлюз, у которого
заявлена мультимодальная модель `qwen3.5-9b` (Qwen, Apache 2.0): она закрывает
и планировщик, и VLM-аудит, а цена предсказуема (20 ₽/1M ввода, 30 ₽/1M вывода).

**Решение.**
1. Добавлен провайдер `aitunnel` с отдельными переменными (`AITUNNEL_BASE_URL`,
   `AITUNNEL_API_KEY`, `AITUNNEL_LLM_MODEL`, `AITUNNEL_VLM_MODEL`,
   `AITUNNEL_TIMEOUT_SEC=120`, `AITUNNEL_MAX_RETRIES=1`), а также отдельный
   выбор для VLM-аудита: `VLM_PROVIDER=ollama|aitunnel|openai_compat|off`.
2. Клиент — тот же `OpenAICompatClient` (httpx), что и для других совместимых
   шлюзов: протокол идентичен, добавлены таймаут, один повтор на сетевых сбоях
   и 5xx/429 и маскирование ключа в логах (первые 8 символов). SDK `openai` не
   подключаем: это лишняя зависимость в образе и второй HTTP-путь для того же
   протокола — выгоды нет, а риск расхождения поведения есть.
3. Ключ — только в `.env` (в `.gitignore`, стережёт `scripts/hooks/pre-commit`);
   в отчётах и логах вместо ключа маска.
4. Отказ провайдера не роняет задание: планировщик уходит в офлайн-режим.
   Флаг `DEMO_MODE=true` отключает этот откат, чтобы на живом демо не показать
   «офлайн-колоду» вместо работы модели.
5. В отчёт задания пишется, кто именно собрал колоду: `planning: aitunnel/qwen3.5-9b`
   или `offline-fallback`, для аудита — `aitunnel/qwen3.5-9b` либо `off`.

**Следствия.** (+) пайплайн проверяется end-to-end без GPU и без платных
локальных моделей; (+) архитектура готова к смене провайдера — на финале
достаточно `LLM_PROVIDER=ollama` (или переменных VK-инференса) и, при
необходимости, адаптера; (+) соответствие ТЗ сохраняется, если модель
действительно open-weights ≤ 35B. (−) нужен баланс в кабинете AITUNNEL;
(−) внешний API зависит от сети — поэтому сохранён офлайн-планировщик и
`DEMO_MODE` для честного поведения на демо.

**Проверка перед сдачей.** `python tools/llm_check.py --json-call` и `--vlm`:
убедиться, что модель отвечает и отдаёт валидный JSON; сверить карточку модели
(Qwen, Apache 2.0, ≤ 35B); прогнать `scripts/e2e.sh`.

## ADR-021. Проверка на незнакомом шаблоне и девять вариантов

**Дата:** 2026-09-23 · **Статус:** принято

**Контекст.** ТЗ прямо предупреждает: на финале шаблон будет незнакомым, а
результат демонстрации — три варианта на трёх разных шаблонах (девять
презентаций). Проверять это на тех же файлах, что использовались при разработке,
бессмысленно.

**Решение.**
1. `tools/e2e_unfamiliar.py` генерирует **новый** шаблон: размер 16:10 (12.8×8″),
   своя палитра и шрифты, а все макеты переименованы в `Layout 1..N`. Дополнительно
   в шаблон добавлены слайды-образцы с таблицей, диаграммой и картинкой — чтобы
   парсер извлёк токены из файла, а не догадывался.
2. `tools/e2e_9variants.py` + `scripts/e2e_9variants.sh`: три шаблона × три
   варианта вёрстки на одном контент-пакете, девять PPTX в `data/output/9variants/`
   и `report.json` с таблицей «шаблон × вариант → время, проблемы аудита».

**Замер (живой AITUNNEL, `qwen3.5-9b`).**

Незнакомый шаблон `Layout 1..N`:

| Что проверялось | Результат |
|---|---|
| Роли макетов по структуре | `title 2, content 9` — имена не использовались |
| Композиционные типы | `blank 3, bullets 6, multi_column 1, image_text 1` |
| Колода | 15 слайдов, планировщик `aitunnel/qwen3.5-9b`, 71–82 с |
| Аудит | 0 ошибок; 2–4 замечания `content_off_source` (модель добавила слайды о рисках, которых нет в источниках) |
| Авто-фиксы | все замечания сняты, после фиксов — 0 |
| Экспорт | 3 PPTX (нативные объекты, растровых слайдов 0), PDF 200, HTML 200 |

Девять вариантов (3 шаблона VK × 3 вёрстки, один контент-пакет):

| Шаблон | Слайдов | Ошибок | Замечаний | Время |
|---|---|---|---|---|
| VK WorkSpace | 15 | 0 | 11–12 | 120.6 с |
| ЛЦТ2026 | 15 | 0 | 11 | 135.3 с |
| VK Education | 14 | 0 | 11 | 121.8 с |

Итого 9 презентаций, 0 ошибок аудита, 379.9 с суммарно (каждый шаблон — в
бюджете 5 минут). Оставшиеся замечания — только `content_off_source`: колода
построена по брифу, а контент-пакет VK Tech почти целиком состоит из
текста-заглушки.

**Следствия.** (+) ключевой риск защиты (незнакомый шаблон) проверяется
автоматически и воспроизводимо; (+) девять вариантов собираются одной командой;
(+) результат измеряется, а не декларируется. (−) незнакомый шаблон генерируется
синтетически: он проверяет структурную устойчивость, но не разнообразие
реальных корпоративных вёрсток — на финале остаётся риск нестандартной
композиции, который закрывается деградацией к контентным макетам и сетке профиля.

## ADR-022. Надёжность LLM-планирования: чек-лист, нормализация, запасная модель

**Дата:** 2026-09-23 · **Статус:** принято

**Контекст.** Репетиция на живом AITUNNEL показала: `qwen3.5-9b` не всегда
соблюдает жёсткие ограничения схемы — первый слайд не титульный, 16 слайдов
вместо 15, семь буллетов, данные фактоидов в `items`. Каждая неудачная попытка
стоила 20–70 секунд, а после трёх сервис уходил в офлайн-планировщик: демо
показывало бы «offline-fallback» вместо работы модели.

**Решение.**
1. **Чек-лист ограничений в конце user-промпта** (версия 1.3): модели лучше
   удерживают инструкции в конце контекста, чем в середине. Перечислены ровно
   те правила, которые проверяет схема.
2. **Детерминированная нормализация** (`planner/normalize.py`) до валидации:
   титульный слайд первым (переносом существующего, а не подменой), обрезка до
   15 слайдов, ≤6 блоков и ≤6 буллетов, переименование незнакомых типов блоков,
   подстановка заголовка и языка. Содержание не трогается: длинные буллеты,
   выдуманные цифры и пустые слайды остаются аудиту, иначе проверки перестанут
   что-либо ловить.
3. **Запасная модель** (`AITUNNEL_FALLBACK_MODEL=qwen3.5-27b`, тоже открытые
   веса ≤ 35B): одна попытка, если основная не дала валидную колоду.
4. Правки нормализации не скрываются: они попадают в отчёт задания
   (`planner.normalizations`).

**Замер после правок** (незнакомый шаблон, три прогона подряд):
успех **с первой попытки**, 13.1 / 14.0 / 21.7 с, 14–15 слайдов, нормализация не
потребовалась. В репетиции демо планирование заняло 10.6 с.

**Следствия.** (+) демо предсказуемо и укладывается в бюджет; (+) ошибки
структуры исправляются мгновенно и детерминированно; (+) модель-запасной вариант
страхует от деградации качества. (−) нормализация может «потерять» слайды
сверх лимита 15 — это осознанное требование ТЗ, а не потеря данных.

## ADR-023. Переключение провайдера на лету — план Б на живом демо

**Дата:** 2026-09-23 · **Статус:** принято

**Контекст.** ТЗ требует живого прогона, а не видео. Внешний шлюз может
отвалиться в самый неподходящий момент; перезапуск сервиса ради смены
провайдера — лишние 5–10 секунд паузы и риск на сцене.

**Решение.** `POST /api/provider` меняет провайдера планировщика и VLM без
перезапуска: `aitunnel | openai_compat | ollama | offline` (для VLM ещё `off`).
Настройки меняются в объекте настроек процесса, поэтому следующее же задание
идёт другим путём. В UI — два селектора и кнопка «применить» в панели отчёта.
Ярлыки честные: при выключенных моделях провайдер называется `offline`, а не
`ollama`/`aitunnel` (иначе отчёт вводил бы в заблуждение).

**Проверено:** `health` показывает активного провайдера и доступность;
переключение на `offline` → `applied=offline, disabled=true, vlm=off`, колода
собирается офлайн-планировщиком; возврат на `aitunnel` → `available=true`.

**Следствия.** (+) план Б выполняется одной кнопкой и мгновенно; (+) состояние
видно в UI; (+) тесты покрывают переключение и валидацию входа.
(−) переключение действует на новые задания, текущее продолжает работу прежним
провайдером.

## ADR-024. Визуальное качество слайдов: фон, декор, контент, нумерация

**Дата:** 2026-09-25 · **Статус:** принято

**Контекст.** Аудит был зелёным, а слайды выглядели плохо: на KPI-слайде
VK Education подписи оказались тёмными на тёмной плашке макета (`#262626`) и не
читались; длинный абзац обрезался краем слайда; модель иногда присылала блоки
без данных (пустой слайд) и дублировала пункты; последовательности рисовались
обычными буллетами. Причина — не модель, а рендер и вёрстка.

**Решение (по пунктам диагностики).**

1. **Цвет текста по фактическому фону.** Профиль шаблона теперь хранит декор
   макета и мастера с заливками (обход групп рекурсивный, для картинок берётся
   доминирующий цвет по непрозрачным пикселям). Рендер выбирает цвет текста и
   акцента по фону **под конкретным блоком**, а не по палитре; аудит считает
   контраст к тому же фону. До правки: 0 из 92 фигур декора имели цвет
   (сломанный `getcolors()`), текст на плашке пропадал. После: 72 из 92.
2. **Контент.** Нормализация выбрасывает блоки без данных (иначе пустой слайд),
   схлопывает дубликаты пунктов, режет абзац длиннее 180 символов на пункты:
   у VK Education минимальный кегль шкалы 32 pt, и абзац физически не влезает.
3. **Последовательности.** Добавлен `kind=numbered` — настоящая нумерация
   PowerPoint (`buAutoNum`), а не текст «1.»; `steps` рисуется шевронами.
   В промпте планировщика (версия 1.4) этапы, шаги и дорожная карта — только
   `numbered` или `steps`.
4. **Аудит.** Порог переполнения текста ужесточён (10% вместо 75%) — теперь
   обрезанный абзац ловится, а не проходит как «норма».

**Проверено:** матрица аудита 6 шаблонов × 3 варианта — 0 ошибок и 0 замечаний;
визуальный осмотр PNG (KPI-слайд читается, шевроны и нумерация на месте, декор
шаблона виден); `slide_too_sparse` больше не появляется на слайдах с блоками.
Тесты: 163 passed, включая новые на пустые блоки, дубликаты, длинный абзац,
`numbered` и контраст к фону.

**Следствия.** (+) слайды читаемы независимо от декора шаблона; (+) меньше
замечаний аудита при том же содержании; (+) нумерация редактируется средствами
PowerPoint. (−) векторный декор (EMF/WMF) цвета не отдаёт — для него
используется фон слайда, ограничение зафиксировано.

## ADR-025. Структурные роли на чужих шаблонах: тело-подзаголовок, фон, колонки

**Дата:** 2026-09-25 · **Статус:** принято

**Контекст.** Критерий ТЗ №3 — адаптация к произвольному корпоративному шаблону.
На трёх сторонних шаблонах (MIT-лицензии) классификатор ролей ошибался системно:

| шаблон | до правок | после правок |
|---|---|---|
| Slidesgo «Anatomy Lesson» (31 макет) | 18 title / 3 section / 10 content | 8 title / 3 section / 20 content |
| Slidesgo «Fun Education Center» (31) | 17 title / 6 section / 8 content | 9 title / 3 section / 19 content |
| Китайский академический scholar-ppt-cn (7) | 7 content, ни одного титула | 2 title / 5 content |

Причины (все воспроизведены на реальных файлах, а не на догадках):
1. **Slidesgo объявляет тело слайда подзаголовком** (`ph=SUBTITLE`, 8.44×3.97″
   при заголовке 0.59″). Эвристика «есть подзаголовок → обложка» уводила в
   `title` все контентные макеты. Но у стандартной обложки Office подзаголовок
   тоже крупный (11.46×2.6″ против заголовка 11.46×1.98″) — по одной геометрии
   случаи неразличимы.
2. **Картинка во весь слайд** (фон Slidesgo, 100% площади) считалась контентной
   картинкой: любой макет с заголовком получал тип `image`.
3. **Подчёркивания в именах**: `TITLE_ONLY` не совпадал с ключом «title only»,
   поэтому макет уходил в структурную ветку «заголовок без контента».
4. **Китайские имена** (`标题幻灯片`, `标题和内容`) не были в словаре, а рамок на
   макетах нет вовсе — они живут на образце. Без имени макет неразличим.

**Решение.**
1. `body_like_subtitles()`: подзаголовок считается телом, если (а) он в 2.5+ раза
   больше заголовка по площади, либо (б) подзаголовков несколько (обложек с двумя
   не бывает). Явное имя — tie-breaker: «титульный слайд» оставляет подзаголовок
   подзаголовком, «с телом/текстом/колонками» — делает телом. Порог 2.5×
   подобран по замерам: Office-обложка даёт 1.31×, Slidesgo-тело — 6.7×.
2. `_layout_shape_kinds()`: картинка ≥85% площади слайда — фон (декор), а не
   контентная картинка.
3. `_named_role()`: разделители имён (`_`, `-`, `.`) приводятся к пробелам.
4. Словарь ролей дополнен: `body`, `text`, `column`, `list` и китайские
   `标题幻灯片`/`封面`, `目录`/`议程`, `章节`, `内容`/`文本`/`列表`, `谢谢`/`感谢`.
   Важно: полная фраза «标题幻灯片», иначе «标题和内容» (заголовок и содержимое)
   тоже стал бы обложкой.
5. Порядок ветвей: имя проверяется до «пустого макета» — иначе пустые макеты
   китайского шаблона никогда не доходили до ролевой ветки.
6. Правило «1 заголовок + 2 и более блока → `multi_column`» (было 4+), как в
   требованиях этапа: два равноценных блока — это две колонки, а не список.

**Проверено.** Матрица аудита 3 шаблона × 3 варианта: 0 ошибок (было 0, но
13+9 ложных `slide_too_sparse` — контент терялся в планировщике, см. ADR-026);
e2e на контент-пакете VK Tech: PPTX/PDF/HTML выгружаются (387/228/499 КБ PDF);
скриншоты — `docs/evidence/external/`; профили шаблонов — там же (JSON).
Тест на инвариантность: переименование макетов в «Layout N» не меняет
композиционные типы и не меняет роли, кроме пары section↔content у разделителя
(у него «заголовок + тело», и роль выводится только из имени).

**Следствия.** (+) роли выводятся из структуры, имя — tie-breaker, как и
требует ТЗ; (+) слайды с фоном больше не выбирают «image»-макет; (−) разделитель
без имени в шаблоне остаётся контентным макетом — ограничение зафиксировано.

## ADR-026. Контент из полей вне схемы не теряется (спасение в нормализации)

**Дата:** 2026-09-25 · **Статус:** принято

**Контекст.** На реальном прогоне (шаблон Slidesgo, контент-пакет VK Tech)
Qwen3.5 положила текст каждого слайда в поле `subheading`, оставив `blocks`
пустыми: 13 из 14 слайдов вышли с одним заголовком. `subheading` — легальное
поле схемы, но рисуется только на титуле и разделе, поэтому содержание молча
терялось. Аудит честно показал `slide_too_sparse` («заполнено 0%») — то есть
проверка сработала, а вот планировщик отдал пустую колоду.

**Решение.** Двумя слоями:
1. **Промпт** (planner/user v1.5): добавлены жёсткие ограничения «содержание —
   только в blocks: слайд типа content без блоков считается пустым» и
   «subheading — короткий подзаголовок для титула и раздела».
2. **Нормализация** (`_rescue_stray_text`): если после чистки у слайда нет
   блоков, текст из `subheading` (кроме титула и раздела) и из полей вне схемы
   (`body`, `content`, `text`, `description`, `summary`, `items`, `bullets`,
   `subtitle`) переносится в блок `text`/`bullets`. Схема остаётся источником
   истины, но содержание не теряется; правка попадает в список нормализаций
   задания и видна в отчёте.

**Проверено.** Тот же прогон после правки: Anatomy — 0 ошибок и 0 замечаний
(было 13 замечаний), Fun Education — 0 ошибок и 0–1 замечание, слайды с
KPI-фактоидами («40%», «12», «5», «2000») на месте. Тесты: 170 passed, включая
`test_subheading_on_content_slide_becomes_block` и
`test_stray_fields_are_moved_to_blocks`.

**Следствия.** (+) модель может ошибаться в схеме, но колода не выходит пустой;
(+) ошибки планировщика видны в `normalizations`, а не только в аудите;
(−) эвристика «текст в subheading → блок» может продублировать подзаголовок,
если модель положила туда короткую подпись, — поэтому для титула и раздела
правило отключено.

## ADR-027. Визуальный чек-лист и правки вёрстки (этап D, критерий ТЗ №4)

**Дата:** 2026-09-25 · **Статус:** принято

**Контекст.** Детерминированный аудит был зелёным, а глазами слайды выглядели
плохо: KPI-числа чёрные и прижаты к верхнему краю, подписи factoid'ов наезжают
друг на друга, текст шевронов вылезает за фигуры, вертикальный заголовок
китайского шаблона обрезан, на слайде с тремя блоками нижняя половина пустая.
Причина — не модель, а рендер, вёрстка и слепые пятна аудита.

**Метод.** `tools/visual_pass.py`: по каждому слайду считаются измеримые
признаки чек-листа (заполненность слайда и его половин, акцент шаблона,
максимальный кегль, минимальный контраст, строки-сироты, число текстовых фигур)
и складываются PNG для осмотра глазами. Прогон: 3 сторонних шаблона × 3 варианта
+ 4 шаблона VK и синтетические фикстуры.

| Пункт чек-листа | Как проверяли | Что нашли | Слой правки |
|---|---|---|---|
| 1. Заголовок — вывод | осмотр + `heading` в отчёте | ок (заголовки-выводы у модели) | — |
| 2. Воздух вокруг блоков | заполненность, осмотр | factoid прижат к верхнему краю ячейки | renderer |
| 3. Выравнивание по сетке | `misaligned_to_grid` | ок | — |
| 4. Контраст ≥ 4.5:1 | `contrast_too_low` + min_contrast | акцент #0097A7 как мелкий текст не проходил 4.5:1 | renderer |
| 5. Палитра шаблона (акцент) | `accent_used` | акцент не использовался: `_accent_color()` возвращал почти белый `#F3F3F3` | renderer |
| 6. Визуальный якорь | max кегль, осмотр | KPI-значения мельче нужного, шевроны переполнены | renderer |
| 7. Правая/нижняя половина | заполненность половин | KPI-слайды: низ пустой (0.00) | renderer + audit |
| 8. KPI читается за 2 с | переносы, наложения | «5 подразделений» наезжало на подпись | renderer |
| 9. Титул не перекрыт декором | вертикальный заголовок | заголовок обрезан в вертикальной рамке | renderer |
| 10. Нет сирот | `orphans` | 1–3 на слайд у scholar (частично ложные: CJK-шрифт) | tool |

**Правки (13, из них 9 в слое рендера/вёрстки и 4 в планировщике/промпте).**

Рендер и вёрстка:
1. `_fit_size`: проверяется итоговый кегль после снапа к шкале и сдвига
   `type_scale_step` — иначе подпись шеврона 14 pt превращалась в 22 pt и
   наезжала на соседний шеврон.
2. Заголовок подбирается под рамку, включая вертикальные (`bodyPr/@vert`):
   в шаблоне scholar заголовок обрезался по высоте.
3. `_accent_color()` берёт акцент из `DesignContext` (тема → accent1/dk2 →
   насыщенная тёмная краска), а не «пятый цвет палитры»: на Slidesgo это был
   почти белый `#F3F3F3`, из-за чего акцент всюду подменялся чёрным.
4. `_accent_on()`: порог контраста как у аудита (3:1 для крупного текста,
   4.5:1 для обычного) — акцент используется только там, где читается.
5. Factoid: рамки считаются от снапнутого кегля и с учётом переноса; значение
   подбирается под остаток ячейки, предпочитая одну строку; группа
   «значение + подпись» центрируется по ячейке.
6. `lines_needed()`: слово длиннее строки занимает несколько строк, а не одну —
   из-за этого кегль выбирался втрое больше нужного.
7. `CHAR_FACTOR` 0.53 → 0.56 и вычет внутренних полей рамки (0.25″): полужирный
   Georgia «в притирку» переносился на вторую строку.
8. Аудит: слайды-фактоиды и цитаты не считаются «пустыми» (`slide_too_sparse`) —
   лаконичность там по замыслу.
9. Аудит: `text_overflow` сравнивал дюймы с EMU и не срабатывал никогда
   (найдено на этапе G, здесь подтверждено на KPI-слайдах).

Планировщик и промпт:
10. Офлайн-планировщик не строит диаграмму из несопоставимых величин
    (3 города / 150 000 человек / 870 руб. / 18 %): столбцы нечитаемы.
11. Подзаголовок обложки — суть брифа, а не шаблонное «проект: цели, объём,
    команда, сроки — краткий обзор».
12. Заголовок обложки обрезается до 60 символов по границе запятой: длинная
    фраза с метриками не влезала в рамку титульного макета.
13. Промпт `planner/system` v1.5: цифры собирать в один слайд-фактоид (до 4
    значений), не больше двух KPI-слайдов, диаграмма — только для сопоставимых
    величин.

**Проверено.** Матрица аудита 8 шаблонов × 3 варианта: 21 из 24 комбинаций
полностью чистые, остальные — только замечания (`text_overflow` на 16:10-мутации
и VK Tech, `overlap` в карточках VK Tech), ошибок нет нигде. Скриншоты «до/после»
(5 пар) — `docs/evidence/visual/`: KPI (акцент+центрирование), шевроны,
вертикальный заголовок, карточки, наложение factoid'ов. Тесты: 179 passed.

**Следствия.** (+) слайды используют палитру и акцент шаблона; (+) крупные числа
читаются и не наезжают на подписи; (+) текст вписывается в рамки всех виджетов
(шевроны, заголовки, карточки), включая вертикальные; (+) аудит видит то, что
раньше пропускал. (−) на 16:10-мутации остаются замечания `text_overflow` —
плотная сетка шаблона; (−) перенос длинных слов (LibreOffice) может отличаться
от оценки — модель оценки консервативна.

| FLUX.2 [klein] 9B | некоммерческая | там же: 9B выпущен под non-commercial | нет |
| FLUX.2 [pro/max/flex] | только API | BFL API, веса не открыты | нет |
| SDXL / SD3 | OpenRAIL / Stability | не Apache 2.0 | нет (по ТЗ) |
| gpt-image, gemini-image, mai-image | проприетарные | — | нет |

**Решение.** Стадия `imagegen` встроена в пайплайн:

1. Блок `kind=image` с полем `image_prompt` (промпт планировщика v1.6 просит
   описание иллюстрации, когда в контент-пакете подходящей картинки нет).
2. `backend/app/imagegen.py` — клиент OpenAI-совместимого
   `/images/generations`; провайдеры: `aitunnel` (модель `flux.2-klein-4b`,
   Apache 2.0) или любой `openai_compat`; по умолчанию `IMAGE_PROVIDER=off`.
3. Картинка встраивается нативно (`add_picture`) с сохранением пропорций:
   размер задаётся `IMAGE_SIZE=1280x720`, рендер вписывает её в слот макета.
4. **Fallback-цепочка:** картинка из контент-пакета (приоритет) → генерация →
   слот-плейсхолдер шаблона (аудит честно помечает `image_missing`
   предупреждением). Недоступность провайдера не роняет задание: причина
   попадает в отчёт `result.imagegen`.
5. Бюджет: `IMAGE_MAX_PER_DECK` (по умолчанию 4), `IMAGE_TIMEOUT_S=60`.

**Замеры** (живой прогон, задание `772080ec532b`, шаблон Slidesgo, бриф о
сервисе): одна картинка **3.6 с** (цель ≤10 с); колода с иллюстрацией целиком
216 с при бюджете 420 с (доминирует VLM-стадия 186 с, генерация — 3.6 с);
картинка в PPTX — нативный объект 5.77×3.24″ с исходными пропорциями 1.78;
аудит: 0 ошибок и 0 замечаний во всех трёх вариантах. Тесты:
`backend/tests/test_imagegen.py` (6 тестов: слот, приоритет контент-пакета,
недоступность провайдера, бюджет, отсутствие промпта).

**Следствия.** (+) ТЗ-задача со звёздочкой закрыта: иллюстрации генерируются,
лицензии подтверждены первоисточниками, есть честный fallback; (+) стадия
выключена по умолчанию — зачётная конфигурация не зависит от внешнего шлюза;
(−) локальный запуск FLUX.2 [klein] на CPU не проверялся: 4B-модель требует
~13 ГБ VRAM, на CPU генерация занимает минуты — в репозитории это опция, а не
путь по умолчанию (честная фиксация, как требует ТЗ).
